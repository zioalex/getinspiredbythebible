# BITB-093: Reconcile the Production Schema with the ORM Models

**Status:** 🎯 Todo
**Priority:** P1
**Size:** M
**Created:** 2026-08-10
**Blocks:** BITB-089 Stage 2 (stamping production) — and therefore BITB-090 and BITB-091.

## User Story

**As a** maintainer about to make Alembic authoritative, **I want** production's schema and the ORM
models to agree, **so that** `alembic stamp r0001` is a true statement rather than a promise that
the next `--autogenerate` will contradict.

## Why Now

BITB-089 Stage 1 found what it was designed to find. `alembic check` against a restored copy of
production returns a non-empty diff, so the `r0001` baseline — autogenerated against a local
database — does not describe production. Stamping would assert a match that does not exist, and
every future autogenerate would try to "fix" the difference.

### What the copy actually shows

Restored from a production schema-only dump and inspected with `\d+`:

| | production | `scripts/init.sql` | ORM models |
| --- | --- | --- | --- |
| `verses.book_id`, `verses.chapter_id` | nullable | `NOT NULL` | `NOT NULL` |
| `chapters.book_id` | nullable | `NOT NULL` | `NOT NULL` |
| `verses` unique constraint | `verses_book_id_chapter_number_verse_number_translation_key` | `unique_verse_translation` | `unique_verse_translation` |
| `chapters` unique constraint | `chapters_book_id_number_key` | `unique_chapter` | `unique_chapter` |
| `verses_translation_fkey` | no delete action | `ON DELETE CASCADE` | `ondelete="CASCADE"` |
| `verses.translation` | `NOT NULL DEFAULT 'kjv'` | same | `default="kjv"` (Python-side only) |

Note the last row matches while the rest do not. That is the diagnosis: production's `verses` was
created by `create_all()` from an older revision of the models — hence the Postgres-generated
constraint name, the nullable FK columns and the missing delete action — and later *extended* by
hand-rolled SQL that added `translation` with a server default. `create_all()` never ALTERs an
existing table, so every model change since those tables were first created has lived in code only.

This is BITB-090's "two competing schema authorities" as a measured fact rather than a risk.

Separately, `books.abbreviation` and `verses.embedding` carry a column comment whose text is the
literal string `comment`. Nothing in this repository sets a column comment — no `COMMENT ON`
anywhere, no `comment=` on any model — so it was applied by hand at some point. Harmless, but it
appears in every autogenerate diff until removed.

## Approach: converge production, then stamp

The alternative — stamp first, fix afterwards with a follow-up revision — was rejected. Stamping
`r0001` asserts production matches it, which is false, and the corrective revision would also run
against a fresh CI database built *from* `r0001`, where `RENAME CONSTRAINT unique_chapter` fails
because the constraint is already named that. That forces a conditional, idempotent migration:
more moving parts, and easy to get subtly wrong. Converging first keeps `r0001` honest.

The reconciliation runs in both directions, chosen per item by which side is right:

**Production is right — change the models (no DDL, zero risk).** Seven columns have a database
level default that no model declares, so the ORM claims there is none:
`translations.license` / `.is_default` / `.created_at`, `contact_submissions.created_at` /
`.status`, `feedback.created_at`, `verses.translation`. Adding `server_default=` makes the models
describe what is deployed. Removing the defaults from production instead would break any raw-SQL
insert path that relies on them.

`r0001` gains the same defaults. It has never been applied to any database — production is
unstamped and CI rebuilds from scratch every run — so editing the baseline in place is legitimate
and is the only way to keep the CI `alembic check` green.

`blocked_message_samples` is deliberately excluded: no SQL script ever created it, so it came from
`create_all()` alone and already matches the models.

**The models are right — change production** (`scripts/reconcile-prod-schema.sql`): `SET NOT NULL`
on the nine columns above, rename the two constraints, add the FK delete action, drop the two stray
comments. Both `init.sql` and the models agree on every one of these; production is the outlier.

### Notes on the DDL

- **Rename, don't rebuild.** Autogenerate proposes DROP + ADD for the constraint names, which
  rebuilds a unique index across the whole of `verses` under an ACCESS EXCLUSIVE lock.
  `ALTER TABLE ... RENAME CONSTRAINT` is metadata-only and instant.
- **The FK cascade is behavioural, not cosmetic.** After it, deleting a row from `translations`
  deletes every verse of that translation. It is in its own section of the script so it can be
  skipped or deferred deliberately.
- **The script fails closed.** Every NOT NULL is preceded by a NULL count that aborts the
  transaction if non-zero, and it refuses to run against an empty `verses` — a schema-only copy has
  no rows, so a zero NULL count there proves nothing. `-v allow_empty=1` skips those checks (loudly,
  with a NOTICE saying the run proves nothing about production data) so a schema-only copy can still
  be used to rehearse the DDL. Production runs without the flag, guards armed.
- **Orphaned translation codes are checked up front.** They would otherwise fail
  `VALIDATE CONSTRAINT` in the last step, after the earlier steps have already committed.

## Out of Scope — and one known blind spot

`compare_type=False` is set deliberately (`api/alembic/env.py`) because `Vector(dim)` differs by
environment: 1024 for the ollama-backed local/CI default, 1536 for `azure_openai` in production.
It suppresses **all** type comparison, not just vectors — so a `timestamp` vs `timestamptz`
mismatch, for instance, is invisible to `alembic check` and to this story.
`translations.created_at` is `DateTime` (no timezone) while `feedback.created_at` and
`contact_submissions.created_at` are `DateTime(timezone=True)`, which is exactly the shape of
difference that would hide there.

A column-by-column type audit against production is **not** covered here. It should be its own
story before anyone concludes the schema is fully reconciled.
