# BITB-089: Deploy Alembic Migrations from CI — Make the Framework Actually Load-Bearing

**Status:** ✅ Done (2026-08-15)
**Priority:** P1
**Size:** M (one-time operator step + workflow wiring)
**Created:** 2026-07-31
**Depends on:** BITB-004 (Alembic framework, PR #948) — merged but **inert** until this story ships.
**Unblocks:** BITB-090 (removing `create_all()`).

## User Story

**As a** maintainer who has just merged the Alembic framework, **I want** a committed Alembic
revision to actually reach the production database on deploy, **so that** "we have a migration
system" is a true statement rather than a framework nobody is wired to.

**As an** operator, **I want** the one-time cutover to be a written, rehearsed procedure,
**so that** adopting Alembic on a live database is not improvised.

## Why Now

BITB-004 (#948) added Alembic, a baseline revision, and a CI job that validates migrations against
an ephemeral database. It deliberately did **not** touch production or the deploy pipeline. The
result is a gap that is easy to misread as "done":

1. **Production has never seen Alembic.** The prod schema was built by `scripts/migrations/`.
   There is no `alembic_version` table. Running `alembic upgrade head` against prod today would
   try to *create* tables that already exist, and fail.

2. **A new revision would silently never deploy.** The deploy workflow's path filter watches
   `scripts/migrations/**` (`.github/workflows/azure-deploy.yml:167`). A revision added under
   `api/alembic/versions/**` matches nothing, so `run-migrations` (`:1439`) does not run. No
   error, no warning — the migration is simply never applied. This is the dangerous half: the
   failure mode is silence, and the schema drift is discovered later by a 500.

The framework is safe today precisely *because* it is inert. This story makes it load-bearing,
which is also the moment CI gains the ability to write DDL to production — so it wants its own
review, not a footnote in a larger PR.

## Rollout, in this order

The order is not stylistic. Wiring the pipeline before stamping points a `upgrade head` at a
database that has the schema but not the bookkeeping — it will fail on the first deploy.

### Stage 1 — rehearse against a restored copy

Restore production into a throwaway target and confirm the baseline actually matches reality,
using Scenario A or C of [`docs/HOW-TO-BACKUP-RESTORE-DATABASE.md`](../HOW-TO-BACKUP-RESTORE-DATABASE.md).

```bash
DATABASE_URL="<restored-copy>" alembic check
```

**This is the gate for the whole story.** `r0001` was autogenerated against a *local* database. If
`check` reports drift against a real copy of prod, prod does not match the baseline and stamping
would paper over a genuine difference. Reconcile before continuing — do not stamp a mismatch.

### Stage 2 — stamp production (one-time, manual, operator-run)

```bash
DATABASE_URL="<prod-url>" alembic stamp r0001
```

`stamp` writes one row to `alembic_version` and executes **zero DDL**. Take a backup first anyway
(Scenario D); rollback is `DROP TABLE alembic_version`.

Verify: `alembic current` reports `r0001`, and `alembic upgrade head` is a no-op.

### Stage 3 — wire the deploy pipeline

Three edits to `.github/workflows/azure-deploy.yml`:

| Line   | Today                                         | Needs to become                                    |
| ------ | --------------------------------------------- | -------------------------------------------------- |
| `:167` | filter watches `scripts/migrations/**`         | also watch `api/alembic/versions/**`                |
| `:1470`| `pip install asyncpg pydantic pydantic-settings` | must include `alembic` (e.g. `-r api/requirements.txt`) |
| `:1500`| `cd scripts/migrations && python run_migrations.py` | `cd api && alembic upgrade head`               |

🔴 **SSL trap — this will fail on the first run if not handled.** Line `:1498` builds the URL as
`...?ssl=require`. The legacy runner tolerates that because
`get_migration_connection_params()` (`scripts/migrations/utils.py:16`) strips both `ssl` and
`sslmode`. Alembic's `env.py` goes through `get_async_database_url()`, which pops **only
`sslmode`** (`api/scripture/database.py:37`). Reusing the URL verbatim leaks `ssl=require` into
the asyncpg connection and fails with `parameter 'ssl' cannot be changed now`. Either emit
`sslmode=require` for the Alembic step, or extend the helper to strip `ssl` as well — and cover
whichever you choose with a test.

Keep the legacy `run_migrations.py` invocation alongside Alembic for at least one deploy so a
failure in the new path does not block an unrelated release.

### What this story learned the hard way

Two findings worth carrying forward:

1. **The Stage 1 gate earned its place.** `r0001` was autogenerated from a local database and did
   not describe production: `verses` and `chapters` had been created by an old `create_all()` and
   never ALTERed since. Stamping without checking would have made Alembic's view of production
   wrong from its first day. See BITB-093.
2. **Verify a stamp with `alembic check`, not `alembic current`.** The stamp was briefly applied
   before the reconciliation script had run. `current` reported `r0001` and looked perfectly
   healthy — it only echoes the row just written. `check` caught the mismatch immediately. The
   runbook now says so.

**Remaining tidy-up (not blocking):** `r0003` removes the probe's table comment from `sessions`.
