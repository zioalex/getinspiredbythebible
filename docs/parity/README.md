# Parity — Cross-Client Contract & Registry Artifacts (BITB-260)

Home of the cross-client parity knowledge graph's committed artifacts:

- **Stage 1 (BITB-261)** — [`openapi.json`](openapi.json): the committed
  **OpenAPI contract artifact**, a machine-diffable freeze of the FastAPI
  backend's request/response shapes — the contract every client (web, Android,
  iOS-to-come) programs against.
- **Stage 2 (BITB-262)** — [`registry.yaml`](registry.yaml): the
  **capability × client parity registry** (api/web/android/ios) with
  [`graph.json`](graph.json) and [`landscape.md`](landscape.md) as its derived,
  CI-freshness-checked views. See the stage-2 section below.

## What the artifact is

- The same JSON the live service serves at the public, unauthenticated
  [`/openapi.json`](../../api/main.py) path (see `TURNSTILE_SKIP_PATHS` in
  [docs/SECURITY.md](../SECURITY.md)) — **route and schema metadata only, no
  secrets, no env-derived values.**
- Generated by [scripts/export_openapi.py](../../scripts/export_openapi.py) from
  `api/main.py:app`, **fully offline** (see below).
- **Deterministic**: every JSON object's keys are sorted
  (`json.dumps(..., sort_keys=True)` sorts recursively), so path order, schema
  order and key order never churn between regenerations — a diff is meaningful.
- Committed on purpose: PRs that change the API surface also commit the
  regenerated artifact, so reviewers and CI see the contract change explicitly,
  and clients can't silently drift from the backend.

## Zero to running

Prerequisites: the repo's Python venv with the `api/` dependencies installed
(`make setup-dev`, or `pip install -r api/requirements.txt` into any Python 3.12
environment). Nothing else — **no database, no LLM keys, no Docker.**

```bash
# Regenerate the committed artifact:
make parity-export                     # or: python scripts/export_openapi.py

# Verify the committed artifact is up to date (writes nothing):
make parity-check                      # or: python scripts/export_openapi.py --check
```

Both exit 0 on success; `--check` exits 1 with a unified diff on stderr when the
committed artifact is stale. Tests: `python -m pytest scripts/test_export_openapi.py -q`.

### The offline import — how it works

Importing `api/main.py` instantiates `Settings()` (`api/config.py`), a Pydantic
Settings class that reads **every field from the environment** — and whose
`database_url` validator rejects the built-in placeholder DSN.

The offline test suite solves this by running with a `DATABASE_URL` that points
at a database nobody connects to (unit tests mock the DB; only integration
tests need a real PostgreSQL). The export script needs more than a working
import — the artifact must be **machine-independent** — so it *strips* the
caller's environment for the duration of the app import:

- **save/replace/restore `os.environ`** around `from main import app`
  (chosen over a clean-subprocess approach so the export stays testable
  in-process);
- the controlled environment contains **only** the keyless seeds:
  - `DATABASE_URL` — a dummy DSN, never connected to (`app.openapi()` builds
    the document from route/model metadata only; the DB is touched only by the
    lifespan handler, which does not run here);
  - `LLM_PROVIDER=ollama` and `EMBEDDING_PROVIDER=ollama` — the keyless
    defaults, so no `ANTHROPIC_API_KEY` / `OPENROUTER_API_KEY` etc. are
    required;
- plus a few interpreter-level passthrough keys (`PATH`, `HOME`, `LANG`, ...)
  that the Python import machinery itself may consult — none of them is a
  Settings field.

No caller env var — a real `DATABASE_URL`, `LLM_PROVIDER=claude` (with its
required-key check), `EMBEDDING_PROVIDER=azure_openai`,
`MAX_MESSAGE_LENGTH=999`, … — can reach `Settings()`, so the output is
identical on every machine (asserted by the machine-independence test).
Settings additionally reads a `.env` file from the CWD if present; the script
is always run from the repo root, which has no `.env` (only `.env.local` /
`.env.dev`, which it does not read).

Exact invocation, verified offline on a clean checkout:

```bash
python scripts/export_openapi.py           # regenerates docs/parity/openapi.json
python scripts/export_openapi.py --check   # CI stale-artifact gate
python scripts/export_openapi.py --output /tmp/head.json   # materialize a spec elsewhere (CI oasdiff job)
```

## CI

[`.github/workflows/parity-ci.yml`](../../.github/workflows/parity-ci.yml) runs
two jobs on every PR:

1. **Stale-artifact check (hard gate):** `python scripts/export_openapi.py
   --check` — fails the PR if the committed artifact doesn't match the app.
   **Fix:** run `make parity-export` on the same PR and commit the result.
2. **Breaking-changes report (warn-only):** the committed artifact is exported
   from both the PR base and the PR head (`--output` into two checkouts), then
   compared with [`oasdiff/oasdiff-action/breaking`](https://github.com/oasdiff/oasdiff-action)
   (Apache-2.0, official, actively maintained), pinned by tag `breaking@v0`.
   The action posts the breaking-changes report as a PR comment itself; this
   repo does **not** hand-roll any docker-run or comment plumbing.

### oasdiff policy: WARN, not gate — and when it flips

Breaking changes (removed endpoints, renamed/required-ified fields, narrowed
request bodies, changed response types) **do not fail CI today**. The job
reports them as a PR comment (plus a `GITHUB_STEP_SUMMARY` write) so the author
and reviewers see them, but a breaking change is a legitimate decision, not
automatically an error — the backend is young and the client set is small.

**Flip condition (deliberate, later decision):** once the baseline is trusted —
i.e. after the parity registry (BITB-262) has recorded every real client and at
least one release has shipped against a frozen contract — flip the action's
`fail-on-breaking: "true"` input. Until then, do NOT add it; a hard gate that
fires on routine contract work would just be reverted.

## Regeneration workflow

Any PR that touches `api/routes/`, request/response models, or `main.py` must
include the regenerated artifact:

1. Make the API change;
2. `make parity-export` and commit `docs/parity/openapi.json` alongside it;
3. The `parity-ci` stale check verifies it on the PR (it fails if you forget);
4. The oasdiff job comments any breaking changes for your reviewers.

Never hand-edit `docs/parity/openapi.json` — regenerate it.

## Stage 2 — the parity registry (BITB-262)

[`registry.yaml`](registry.yaml) is the store of record: every user-facing
capability × client (`api`, `web`, `android`, `ios` planned per BITB-087) with a
parity status (`synced | drifted | partial | absent | obligated | n/a`), concrete
evidence refs (file paths, PRs, stories), the cross-client **contracts**
(chat-stream-sse, citations-spans, verse-grammar, strings-catalog,
telemetry-os-enum, platform-flags, permissions, legal-urls), and **negative
obligations as first-class rows** (`ios-no-verse-regex`, `ios-no-donate-entry`).

Derived, committed views — never hand-edit, regenerate:

| Artifact | What |
|---|---|
| [`graph.json`](graph.json) | The machine graph (nodes/edges/rollups) BITB-263's on-demand Neo4j lens imports |
| [`landscape.md`](landscape.md) | The Mermaid container diagram + capability×client status matrix + drift watch |

### Zero to running

Prerequisites: Python 3.11+ with `jsonschema` and `PyYAML`
(`pip install jsonschema PyYAML` — CI pins `jsonschema==4.26.0 PyYAML==6.0.3`).
No database, no keys, no network.

```bash
python tools/parity-graph/analyze.py     # validate registry → graph.json
python tools/parity-graph/render.py     # → landscape.md
make parity-registry-check               # both freshness gates (what CI runs)
python tools/parity-graph/render.py --summary   # the drift watch (informational)
python -m pytest tools/parity-graph/ -q         # the tool's tests (offline)
```

### What the validation guarantees

- **Schema** — [the registry validates](../../tools/parity-graph/registry.schema.json)
  (jsonschema): status vocabulary, evidence required for synced/drifted/partial,
  story required for obligated.
- **Rows are TRUE, not plausible** — every evidence entry that looks like a repo
  path is existence-checked on every run.
- **Strings cross-check shares the Android CI's source of truth** — it re-runs
  the `translation-validation` job's own check with that job's own extraction
  regex, read out of `.github/workflows/android-ci.yml` at runtime; if the job
  changes, the cross-check fails until it matches. No forked validator that can
  disagree.
- **Drifted rows are the payload, not the failure** — the registry job renders
  them in its GitHub step summary and in `landscape.md`; only an invalid
  registry or a stale `graph.json`/`landscape.md` fails CI.

### Row upkeep workflow

1. Read the code — open every file you are about to cite (the 2026-03 WIP
   parity plan is a source of leads, never of truth; re-verify).
2. Edit `registry.yaml`; regenerate and commit `graph.json` + `landscape.md`
   on the same PR.
3. CI (`.github/workflows/parity-ci.yml` → the `registry` job) re-validates.

See [`tools/parity-graph/README.md`](../../tools/parity-graph/README.md) for the
full tool documentation.
